# Синхронизация мест с Google Places

Google sync спрашивает Google Places API (New) об актуальных данных каждого места
и предлагает обновить их в MongoDB (коллекция `newplaces`). Работает в две фазы:

1. `plan` спрашивает Google и пишет **Sync plan**: JSON-файл с предлагаемыми
   изменениями (каждое — одно поле одного места) и читаемую сводку рядом.
   В места **ничего не пишет**.
2. Админ читает сводку, удаляет из JSON то, что применять нельзя.
3. `apply` пишет то, что осталось, и сохраняет **Applied sync** (что записано и
   что было до записи).
4. Если что-то пошло не так, `rollback` возвращает прежние значения.

В места попадает только то, что прошло через `apply` просмотренного плана. Других
путей записи у синхронизации нет: записи сразу после запроса к Google, без
просмотра, больше не существует.

Код: модуль `src/scripts/googleSync.ts` (функции `plan`, `apply`, `rollback`,
`summary`, `budget`) и тонкий CLI `src/scripts/syncGooglePlaces.ts`.

## Что синхронизация трогает

| Поле в базе                   | Откуда из Google                          | Когда попадает в план                           |
| ----------------------------- | ----------------------------------------- | ----------------------------------------------- |
| `properties.openingHours`     | `regularOpeningHours.weekdayDescriptions` | если Google вернул часы и они отличаются        |
| `properties.phone`            | `internationalPhoneNumber`                | если Google вернул номер и он отличается        |
| `properties.website`          | `websiteUri`                              | если Google вернул сайт и он отличается         |
| `properties.businessStatus`   | `businessStatus`                          | если отличается (закрытые скрываются, см. ниже) |
| `properties.googleId`         | `id`                                      | если Google перевёл место на новый Place ID     |
| `properties.googleNotFoundId` | Place ID, на который Google ответил 404   | метка Lost Google match, см. ниже               |
| `properties.googleNotFoundAt` | дата `apply` этой метки                   | ставится и снимается вместе с `googleNotFoundId` |

В плане поле называется без префикса: `businessStatus`, `googleId`,
`openingHours`, `phone`, `website`, `googleNotFoundId`. `googleNotFoundAt`
отдельной записью в плане не бывает. Обоих полей метки нет в GraphQL.

Не трогает: `name`, `address`, `geometry.coordinates`, `description`, `image`,
`instagram`, `additionalInfo`, `neighborhood`. Ничего не удаляет. `apply`
отказывается применять план, в котором руками вписано поле не из таблицы.

Места без `properties.googleId` не запрашиваются. Места с меткой Lost Google
match, у которых `googleId` не изменился, тоже (см. «Lost Google match»).

## Find on Google: поиск Place ID для заявки на добавление места

`findGoogleIdsForSuggestion(id, token)` (GraphQL-резолвер, review-страница
админа) ищет до трёх Google Place ID по имени и адресу заявки — Text Search
(New) с `X-Goog-FieldMask: places.id`. Это SKU **Text Search Essentials IDs
Only**, он бесплатен без ограничения по количеству запросов, в отличие от
Place Details выше — запрашивать любое другое поле здесь нельзя, это увело бы
вызов на платный SKU. Использует тот же `GOOGLE_PLACES_API_KEY`. Text Search
не расходует Sync budget, и дневной лимит на Place Details его не касается.

Как только админ выбирает один из кандидатов и публикует заявку с этим Place
ID, следующий `plan` предложит для нового места часы, телефон и сайт по этому
ID, а `apply` их запишет — отдельного платного вызова при публикации нет.

## Как запускать

**`plan` запускается только против production-базы и только после того, как
выполнен [чеклист раскатки](#чеклист-раскатки-владелец-руками), и только с
согласия владельца.** Каждое место в `plan` — платный запрос. Тестовую или
локальную базу не используйте: тесты подменяют `fetch` и в Google не ходят,
а `plan` против другой базы тратил бы деньги и тот же месячный лимит Google
впустую.

Нужен `.env` с `MONGO_URI` (production) и `GOOGLE_PLACES_API_KEY` (плюс остальные
переменные, которые требует `src/config/config.ts`). Все подкоманды, кроме
`summary`, работают с базой из `MONGO_URI`.

```bash
npm run build
node dist/scripts/syncGooglePlaces.js            # без аргументов: печатает справку, ничего не делает
```

Без сборки, прямо из TypeScript:

```bash
node --no-warnings --loader ts-node/esm src/scripts/syncGooglePlaces.ts budget
```

| Подкоманда                         | Что делает                                                                                     | Google | Пишет в базу |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- | ------ | ------------ |
| (без аргументов)                   | справка                                                                                        | нет    | нет          |
| `plan [--limit=N]`                 | спрашивает Google, пишет Sync plan и сводку; `--limit=N` — только первые N мест по `_id`        | да     | только Sync budget |
| `summary <plan.json>`              | заново строит сводку `.md` из JSON (после правки); к базе не подключается                       | нет    | нет          |
| `apply <plan.json>`                | пишет оставшиеся в плане изменения, сохраняет Applied sync                                     | нет    | да           |
| `rollback <applied.json>`          | возвращает значения, которые заменил `apply`                                                   | нет    | да           |
| `budget`                           | показывает Sync budget месяца и прогоны                                                        | нет    | нет          |
| `budget --set=N --reason="…"`      | ставит потраченное за месяц в N, снимает резервы, закрывает незавершённые прогоны              | нет    | да (бюджет)  |

Неизвестная подкоманда или флаг, неверный `--limit` (0, не число), `apply`/
`rollback`/`summary` без ровно одного файла, `--set` без `--reason` и наоборот —
ошибка со справкой, до подключения к базе.

### Где лежат файлы

Всё пишется в `untracked/google-sync/` относительно текущей директории (папка в
`.gitignore`, данные прода не попадают в git):

| Файл                                   | Кто пишет                    |
| -------------------------------------- | ---------------------------- |
| `<datetime>-plan.json`                 | `plan` — Sync plan            |
| `<datetime>-plan.md`                   | `plan` и `summary` — сводка   |
| `<datetime>-applied.json`              | `apply` — Applied sync, рядом с планом |

`<datetime>` — время запуска в UTC, `:` заменены на `-`, например
`2026-10-06T12-34-56Z-plan.json`. Файлы остаются на той машине, где запускали:
путь к плану записан в прогоне, который показывает `budget`.

### Порядок работы: plan → просмотр → apply → (rollback)

1. `budget` — сколько осталось в этом месяце.
2. `plan --limit=N` или `plan` (полный прогон — все места с `googleId`, кроме
   Lost Google match). Если запросы не помещаются в Sync budget, `plan`
   отказывается **до первого запроса**, ничего не тратит и подсказывает
   `plan --limit=<остаток>` или дату сброса.
3. Прочитать `<datetime>-plan.md` (см. «Как читать сводку»).
4. Удалить из `<datetime>-plan.json` всё, что применять нельзя: отдельную
   запись из `changes` места или всё место из `places`. Удалённое значит «не
   применять». Секции `notFound`, `failed`, `skipped` информационные, `apply`
   их не читает, править их не нужно.
5. `summary untracked/google-sync/<datetime>-plan.json` — пересобрать сводку,
   чтобы она совпадала с тем, что будет записано (по желанию).
6. `apply untracked/google-sync/<datetime>-plan.json` — записать. Печатает каждую
   запись (`written`, `already applied`, `changed since plan`) и путь к
   Applied sync.
7. Если результат плохой: `rollback untracked/google-sync/<datetime>-applied.json`.

Как `apply` решает по каждой записи:

- значение в базе равно `current` из плана → пишется `proposed` (**written**);
- значение уже равно `proposed` → **already applied**, повторный `apply` безвреден;
- что-то третье → **changed since plan**: поле правили после плана, оно не
  перезаписывается. Остальные записи того же места применяются.

Сравнение нормализует значения так же, как `plan` (часы с разными пробелами
равны, отсутствующий `businessStatus` = `OPERATIONAL`, отсутствующие телефон и
сайт = `null`).

`apply` и `rollback` **отказываются** работать, если файл сделан из другой базы
(хост и имя базы из `MONGO_URI`, без пароля). План старше 7 дней применяется, но
с предупреждением: данные Google могли устареть. Частичный план (остановлен на
429) применяется как обычный.

Applied sync переписывается после каждого места, так что и после падения
посреди `apply` в нём есть всё, что успело записаться. В нём `written` (поле,
значение до записи, записанное значение) и `skipped` (с причиной).

`rollback` по каждой записи из `written`: если в базе всё ещё записанное
значение, возвращает прежнее; если поле с тех пор правили (или место удалено) —
**changed since apply**, не трогает. Отдельного файла не пишет, повторный
`rollback` безвреден. Поле, которого до `apply` не было, возвращается как
пустое значение (`null`, `OPERATIONAL`, `[]`).

### Как читать сводку

`<datetime>-plan.md` строится только из JSON (без базы и без Google), по порядку:

- **Partial plan: stopped on 429** — первая строка, только если прогон
  остановился на 429. Неотвеченные места — в Failed с причиной `quota`.
- Заголовок: когда сделан план, из какой базы, с каким `--limit`.
- Счётчики: Looked up, With changes, Unchanged, Not found, Failed, Skipped as
  Lost Google match. Место, у которого все записи удалены из JSON, считается
  Unchanged. В частичном плане Looked up считает только отправленные запросы и
  говорит, сколько из выбранных мест не отправлено (`meta.notSent`); они же
  отмечены в Failed («N of them not sent»).
- **Status changes** — закрытия (`closes`), потом открытия (`reopens`). Смотрите
  первыми: они скрывают и возвращают места на карте.
- **Google Place ID changes** — Google перевёл место на новый ID.
- **Other changes** — по местам: часы как разница по дням (только
  отличающиеся дни), телефон и сайт как «было → стало».
- **Not found** — Google ответил 404; для каждого сказано, есть ли в плане
  метка Lost Google match или её удалили.
- **Failed** — прочие ошибки (сеть, 5xx, `quota`); место не проверено, в
  следующий раз запросится снова. Если `403`, проверьте ключ и billing (см.
  «Google Cloud»).
- **Skipped: Lost Google match** — места с меткой, которые не запрашивались:
  название, адрес, Place ID с 404, когда помечено, и ссылка поиска в Google Maps.
- **Already closed and unchanged: N** — уже закрытые места без изменений, одной
  строкой.

Пустая секция пишет «None.».

## Деньги и квоты: главное ограничение

Запрашиваемые поля (часы, телефон, сайт) относятся к SKU
**Places API Place Details Enterprise**:

- **1000 запросов в месяц бесплатно**, дальше **$20 за 1000** (цены проверены
  в октябре 2026, могут измениться).
- Бесплатные 1000 — **на весь billing account**, общие для всех его проектов.
- Один запрос = одно место. Полный прогон = столько запросов, сколько мест с
  `googleId` без метки Lost Google match (на сентябрь 2026 это 446). Безопасный
  ритм: один полный `plan` в месяц.
- Месяц сбрасывается **1-го числа в 00:00 по US Pacific** (обычно 09:00 по
  Берлину, но 1 ноября — 08:00), а не в местную полночь. Точное время сброса
  по Берлину показывают `budget` и отказ `plan`.
- **Ответ 404 (Place ID не найден) тарифицируется.** Ответ `429` — нет.
- `summary`, `apply`, `rollback`, `budget` в Google не ходят и ничего не стоят.

### Sync budget — счётчик в реальном времени

Свой счётчик запросов синхронизации, в production-базе, общий для всех машин:

- Лимит `SYNC_BUDGET = 900` в месяц (константа в `googleSync.ts`; поднять —
  только осознанным коммитом). Запас до 1000 — на прочие расходы billing
  account и края месяца.
- Месяц — календарный по US Pacific, как у Google.
- `plan` заранее резервирует столько запросов, сколько мест собирается
  запросить. Не помещается — отказ до первого запроса, с остатком и временем
  сброса. Два `plan` одновременно с разных машин честно делят остаток.
- Считается всё, кроме 429: 200, 404, 5xx, сетевые ошибки. По окончании
  неиспользованный резерв возвращается.
- Убитый процесс оставляет резерв висеть (счётчик может быть завышен, но не
  занижен). `budget` показывает такой прогон как `NOT FINISHED`. Если `plan`
  падает с ошибкой посреди прогона, он перестаёт брать новые места, дожидается
  уже отправленных запросов и только потом записывает счёт.
- Если план записан, но обновить счётчик или запись прогона не удалось (база
  отвалилась в конце), `plan` не падает, а печатает `Warning:` с тем, что
  починить через `budget --set`. План при этом полный: смотрите его, а не
  запускайте `plan` заново.
- `budget` — потрачено, зарезервировано, осталось, когда сброс, и прогоны
  месяца (машина, время, резерв, отправлено, исход, путь к плану, коррекции).
- `budget --set=N --reason="…"` — поставить потраченное в N, обнулить резерв,
  закрыть незавершённые прогоны; записывается с причиной. Для начального
  значения при раскатке и после упавшего прогона. Не запускайте, пока идёт `plan`.

### Что показывает Google

Оплачиваемое использование по SKU видно в консоли Google Maps Platform и в
Billing → Reports, **с задержкой до 48 часов**. Страница Quotas показывает
запросы в реальном времени, но источником для счёта не является; Metrics
показывают количество запросов по методам и кодам ответа. Поэтому в реальном
времени смотрите `budget`, а консоль — для сверки.

Бюджет `coffeemap minimal budget` ($1/мес) только **присылает письма** при
50/90/100%, он **не останавливает** расходы. Настоящий spend cap Google для
Places не поддерживает.

### Дневной лимит Google: 500

Вторая линия защиты, на случай обхода Sync budget, бага или утёкшего ключа:
квота `GetPlaceRequest per day = 500` на проекте `berlin-coffee-f0bf8` (ставит
владелец, см. чеклист). Это один полный прогон в день. `GetPlaceRequest per
minute` (600) не трогается. У Text Search свои строки квот (`SearchTextRequest
…`), их лимит на Place Details не касается.

**Правило:** когда мест с Google Place ID станет больше ~450, поднимите дневной
лимит до их количества плюс 10 %.

Квоты Google применяются неточно (могут пропустить чуть больше), сбрасываются
в полночь US Pacific. Месячной квоты у Google нет, месяц держит Sync budget.

### 429: прогон останавливается

Первый `429` (дневной или поминутный лимит) **останавливает прогон**: новые
запросы не отправляются, уже отправленные дожидаются ответа, все неотвеченные
места (и то, что получило 429) попадают в Failed с причиной `quota`. План всё
равно пишется, с `meta.stoppedOn: "429"` и строкой «Partial plan» в начале
сводки: оплаченные ответы не теряются. Повторов нет. Запустите `plan` позже
(после полуночи US Pacific, если сработал дневной лимит).

## Lost Google match

Место, на чей `googleId` Google ответил 404 (не знает такой Place ID).

- В плане оно попадает в `notFound` и получает запись `googleNotFoundId:
  <текущая метка или null> → <Place ID с 404>` (обычно `null`; старая метка
  бывает, если место уже помечали под другим ID). Это обычная запись плана: её можно удалить из JSON,
  если считаете 404 временным сбоем Google, тогда следующий `plan` запросит
  место снова.
- После `apply` у места стоят `googleNotFoundId` и `googleNotFoundAt`. Пока
  `googleId` равен `googleNotFoundId`, `plan` место **не запрашивает** и не
  резервирует под него бюджет: 404 оплачивается один раз, а не каждый месяц.
  Такие места перечислены в сводке в «Skipped: Lost Google match».
- Место **остаётся на карте**: метка ничего не говорит о том, открыто ли оно.
  Его часы, телефон и сайт просто больше не обновляются.

Как починить: по ссылке из сводки найти место в Google Maps, взять новый Place
ID (или через «Find on Google») и поставить его руками. Снимать метку не нужно:
`googleId` больше не равен `googleNotFoundId`, и следующий `plan` запросит место.

```js
db.newplaces.updateOne({ _id: ObjectId("...") }, { $set: { "properties.googleId": "<новый Place ID>" } })
```

Если место закрылось насовсем — закрыть его вручную (см. «Закрытые места»).

Если Google снова узнаёт старый Place ID, снять метку руками, оба поля:

```js
db.newplaces.updateOne({ _id: ObjectId("...") }, { $set: { "properties.googleNotFoundId": null, "properties.googleNotFoundAt": null } })
```

`rollback` Applied sync, в котором была метка, тоже снимает оба поля.

## Закрытые места

Google отдаёт `businessStatus`: `OPERATIONAL`, `CLOSED_TEMPORARILY` или
`CLOSED_PERMANENTLY`. Синхронизация хранит его в `properties.businessStatus`
(по умолчанию в схеме `OPERATIONAL`).

Места со статусом `CLOSED_TEMPORARILY` и `CLOSED_PERMANENTLY` **скрыты из всех списков**,
но остаются в базе. Фильтр лежит в `src/models/Place.ts`:

```ts
export const VISIBLE_PLACE_MATCH = {
  "properties.businessStatus": { $nin: ["CLOSED_TEMPORARILY", "CLOSED_PERMANENTLY"] },
};
```

Где применяется:

| Где                                                    | Эффект                              |
| ------------------------------------------------------ | ----------------------------------- |
| `allPlacesResolver` (`getPlacesWithStats`)             | список и `total`                    |
| `filteredPlacesResolver`                               | фильтры и `total`                   |
| `favoritePlacesResolver`                               | избранное пользователя              |
| `availableNeighborhoodsResolver`                       | список районов для фильтра          |
| `availableAdditionalInfoTagsResolver`                  | список тегов для фильтра            |

Где **намеренно не применяется**: страница места по id (`placeResolver`), история
отзывов пользователя (`userReviewActivityResolver`), лайки и оценки. Старые ссылки
и отзывы продолжают работать.

Статус меняется в обе стороны и только через план: закрытие или открытие места
появляется в сводке в «Status changes». Если временно закрытое место снова
открылось, `apply` поставит `OPERATIONAL`, и место вернётся в выдачу. Между
прогонами статус не меняется, автоматического запуска нет.

Вручную скрыть или вернуть место:

```js
db.newplaces.updateOne({ _id: ObjectId("...") }, { $set: { "properties.businessStatus": "CLOSED_PERMANENTLY" } })
db.newplaces.updateOne({ _id: ObjectId("...") }, { $set: { "properties.businessStatus": "OPERATIONAL" } })
```

Ручной статус сам не перезаписывается: если Google с ним не согласен, следующий
план покажет смену статуса в «Status changes», и её можно удалить из JSON
перед `apply`. Если ручная правка сделана уже после `plan`, `apply` пропустит
это поле как «changed since plan».

**Если добавляете новый запрос, который отдаёт список мест, добавьте в него
`{ $match: VISIBLE_PLACE_MATCH }`**, иначе закрытые места снова появятся.

## Нюансы

### Кэш районов и тегов

Списки районов и тегов кэшируются в памяти сервера на 24 часа
(`src/utils/cache.ts`). После `apply` или `rollback` работающий сервер покажет
новые районы/теги только после перезапуска или истечения кэша. Сами места
обновляются сразу, кэша у них нет.

### Формат часов работы

Google возвращает `Monday: 9:00 AM – 5:30 PM`. Синхронизация приводит к формату,
который уже был в базе: `{ day: "Monday", hours: "9 AM to 5:30 PM" }`:

- `–` → ` to `;
- `:00` убирается (`9:00 AM` → `9 AM`);
- неразрывные пробелы (U+202F перед AM/PM, U+2009, U+00A0) → обычный пробел.

В старых данных перед AM/PM стоит U+202F, поэтому при сравнении пробелы в базе
тоже нормализуются. Без этого почти все места выглядели бы изменёнными.
Выходной день приходит как `Closed`, интервалы через запятую сохраняются как есть.

Часы запрашиваются на английском (`languageCode=en`), под него же рассчитан парсинг.

### Адрес и координаты

Не синхронизируются. В базе адрес хранится коротко (`Chausseestraße 52, 10115`),
а у Google полный (`..., 10115 Berlin, Germany`). Автозамена сломала бы единый формат.

### Условия Google (ToS)

По правилам Google Maps Platform бессрочно хранить можно только Place ID. Остальные
данные Places формально можно лишь кэшировать на ограниченный срок. Проект
сохраняет часы, телефон и сайт в базе. Это осознанный компромисс, но о нём
стоит помнить.

## Чеклист раскатки (владелец, руками)

До этих шагов `plan` не запускается.

1. Смержить и задеплоить новый скрипт. Записи без просмотра плана в нём нет,
   так что старый порядок с сервера уже не запустить.
2. Консоль Google Maps Platform → Billing / Reports: прочитать использование
   **Place Details Enterprise** за этот месяц (задержка до 48 ч; если прогон был
   в последние два дня, округлить вверх).
3. Против production: `budget --set=<это число> --reason="seed from GMP console"`.
4. Google Cloud console → проект `berlin-coffee-f0bf8` → Places API (New) →
   Quotas & System Limits → `GetPlaceRequest per day` → **500**.
   `GetPlaceRequest per minute` и все строки `SearchTextRequest` не трогать.
5. `budget` — убедиться, что цифры месяца верные. Затем, когда синхронизация
   понадобится и владелец даст добро, первый `plan --limit=5`.

Первый `plan` после раскатки один раз оплатит места, которые сейчас отвечают
404 (сколько их — неизвестно), и пометит их через план.

## Для разработчиков и AI-ассистентов

- Никогда не запускайте `plan` без явного согласия владельца, и только против
  production-базы, после чеклиста раскатки. Для проверки логики — тесты, не `plan`.
- Никогда не запускайте `apply` и `rollback` без явного согласия владельца: они
  пишут в базу из `MONGO_URI`.
- Перед любым `plan` смотрите `budget`. При отказе по бюджету не обходите его:
  `plan --limit=<остаток>` или ждите 1-го числа.
- `budget --set` — только по просьбе владельца, с осмысленным `--reason`.
- Тесты в Google не ходят: `tests/support/fakeGoogle.ts` подменяет глобальный
  `fetch` (`useFakeGoogle()`), база — одноразовый mongod. Новые тесты синхронизации
  пишите так же.
- Константу `SYNC_BUDGET` и квоту в Google Cloud не меняйте сами.
- Одноразовые скрипты, которые импортируют сервисы с кэшем (`src/utils/cache.ts`),
  не завершаются сами из-за `setInterval`. Заканчивайте их `process.exit(0)`.
